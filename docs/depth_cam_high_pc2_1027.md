# PC2 cam_high depth 거리 실측 — 10/27

Trossen PC2(새 로봇) cam_high(D405 `230422271108`)의 depth 를 「앞에 보이는 물체까지 거리」 센서로 쓸 수 있는지,
베이스를 앞뒤로 움직이며 오도메트리·줄자와 대조했다. 팔은 움직이지 않았다.

도구: `scripts/depth_probe.py` (카메라 3대 depth 점검·컬러맵) · `scripts/depth_approach.py` (베이스 이동 + 랙 depth 추적).
산출물: `outputs/depth_probe/2026102*` · `outputs/depth_approach/2026102*` (gitignore — 이 PC 에만 있다).

## 방법

- 베이스가 회전 없이 직진하면 고정 물체의 카메라 좌표 P 가 반대로 평행이동한다 → `|P_k − P_0|` = 이동 거리 (카메라 기울기와 무관),
  `f = −ΔP/|ΔP|` = 카메라 좌표의 전진 방향(→ 숙임 각), `P·f` = 목표까지 앞쪽 수평 거리
- 정지마다 15 프레임 픽셀별 중앙값 depth. 랙은 기준 이미지(`outputs/depth_probe/20261027_205657/cam_high_color.png` 의 몸통 crop)
  다중 배율 템플릿 매칭으로 매 정지 새로 찾고, **회색조 < 70 픽셀(검은 몸통)만** 3D 로 편다 — 흰 튜브·책상·벽을 섞으면 +7% 로 틀어졌다
- 안전: 전진 전 Enter, 화면 가운데 절반 폭의 1 퍼센타일 depth < 0.45 m 면 더 전진 안 함(후진은 뒤를 못 봐 사람이 감시),
  이동 절댓값 상한 `--max-travel` 기본 0.5 m. 속도 0.08 m/s

## 함정

- **lerobot `read_depth()` docstring 의 「mm」 는 틀렸다** — 변환 없이 z16 원값을 주고, D405 `depth_scale` = 1e-4 m (0.1 mm).
  원값을 mm 로 쓰면 10배 틀린다. 장치에서 `first_depth_sensor().get_depth_scale()` 로 읽어 곱할 것
- lerobot 은 `rs.align` 을 안 한다. depth/color fx 389 vs 392(≈0.9%), 주점 2~4 px 차 → 가장자리에서 수 px 어긋남.
  픽셀 단위 RGB-D 결합이 필요하면 정렬을 넣을 것
- 이 레포 로봇 클래스는 `cam.async_read()`(컬러)만 관측에 넣는다 (`mobileai.py:493`). `use_depth: true` 만으로는 데이터셋·정책에 depth 가 안 들어간다
- **조명**: D405 는 IR 프로젝터 없는 패시브 스테레오. 소등 상태 유효 픽셀 25~61% → 점등 57~94%, 시간 노이즈 88→31 mm(cam_high, 1.4 m)
- 검은 무광 그리퍼 손가락은 점등 후에도 depth 가 거의 빈다 (손목 하단 절반 유효 22~42%)
- 카메라 3대 color+depth 640×480 동시에 30 fps 유지 (USB 대역폭 문제 없음)

## 회전 측정 — 가능성 확인 (10/27 저녁)

`scripts/depth_rotate.py` 가 제자리 회전(오도 목표 0 → +15 → +30 → 0 → −15 → −30 → 0°, 15°/s)을 하며 정지마다
cam_high 를 받고, `scripts/depth_yaw.py` 의 **RGB-D 비주얼 오도메트리**(ORB 대응 + depth 3D + RANSAC Kabsch, 바닥 평면 기준 yaw)로 회전각을 잰다.
**회전각은 depth 비율 오차(×0.945)와 무관**하다 (방향만 본다). 런: `outputs/depth_rotate/20261027_220528`.

|---|---|---|
| 0→1 | +11.80 | +10.83 |
| 1→2 | +14.14 | +16.65 |
| 2→3 (방향 전환) | −30.52 | −26.32 |

| 4→5 | −14.86 | −16.62 |

- VO 자체 일관성: 같은 장면 0.04° 안 · 이웃 구간 합과 직접 비교가 0.3~1.4° 안 (0→5 −31.33 vs −31.60, 0→6 −0.79 vs −2.24)
- 직진 런에 같은 VO: yaw 0±1.5°, 수평 이동은 depth 비율 오차를 받아 줄자보다 ≈+4.5% (×0.945 하면 줄자와 맞음)
- **오도와 VO 가 구간마다 −4.2~+2.5° 다르다.** 비율도 + 회전 1.02~1.06, 2→3 은 0.86 으로 들쭉날쭉 — 외부 정답(각도기)이 없어
  어느 쪽 오차인지, 방향 전환 때의 체계적 손실인지 이 한 런으로는 못 가른다 [추정]. 비율을 정하려면 같은 계획을 여러 번 반복해야 한다
- 오도 목표 0° 는 시작 확인 동작(≈+3.7°) **전** 원점이라 정지 3 은 정지 0 보다 4.6° 더 오른쪽이어야 맞다(오도 −4.58).
  VO 는 정지 0 대비 +0.70 — 2→3 반대 회전에서 오도가 말한 만큼 실제로 안 돌았다는 쪽 (VO 이웃 합 +1.16 과도 일치)
- **버린 방식** (`depth_yaw.py` 첫 판): 세로 면 법선 방위각 히스토그램은 depth 노이즈가 만든 카메라 고정 법선(방위 0°)에 끌려
  실제 ±30° 회전을 늘 ≈0° 로 냈다. 직진 런에서 「≈0° 나왔으니 통과」 로 본 것도 같은 이유로 무의미했다. 위에서 본 점 지도 상관도 2~39° 틀려 버렸다
- 바닥 평면에서 본 cam_high 높이 ≈ 1.095 m (정지 7개 1.094~1.100)

### 외부 기준 — ArUco 마커 (10/27 밤, `scripts/marker_yaw.py`, 런 `234258`)

- 정지 상태 눕힌 마커 방위 흔들림 ±0.15°
- **세운 마커의 윗변 방향은 못 쓴다** — 정면에서 본 작은 평면의 면내 회전은 원근이 거의 없어 PnP 로 정해지지 않는다(정지 중 ±9°, 회전 구간에서 부호까지 틀림).
  위치(중심)는 정확하니 **두 마커 중심을 잇는 선의 방위각**으로 쓴다 — 눕힌 마커 대비 1.3~1.7° (중심 ≈1 cm 오차 / 44 cm 간격)
- 방향 전환 지연이 외부 기준으로 확인: 왼→오른 전환 다음 구간 오도 −14.02 vs 실제 −18.49 (전환 구간에서 못 돈 ≈5° 를 따라잡음)
- 같은 ID 마커 두 장은 눕힘/세움(기울기 45°)으로 가른다. ±30° 끝 정지에서는 마커가 하나씩 화면 밖 — 둘을 화면 가운데로 모으면 전 구간 가능
- 체커보드(8×6)는 1.2 m 에서 한 칸 ≈12 px 라 검출 안 됨 — 쓰려면 0.6 m 안이나 더 큰 인쇄
