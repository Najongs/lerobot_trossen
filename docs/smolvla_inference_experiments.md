## 현재 쓸 수 있는 구성

| 구성 | 옵션 | 특징 |
|---|---|---|
| 연속 TA (비동기) | `--ensemble.coeff=0.01`(또는 `-0.3`) `--ensemble.amp=bf16` | 측정한 것 중 가장 부드럽다. 클램프 0회, 정지 없음 (E16) |
| 청크 고정 실행 + TA | `--ensemble.commit=30 --ensemble.coeff=0 --ensemble.amp=bf16` | 청크 하나를 30스텝 실행하고, 그 사이 도착한 청크의 평균으로 크로스페이드한다. 시뮬레이션만 했다 (E20) |
| 동기 (TA 없음) | `--ensemble.async=false --ensemble.every=50 --ensemble.amp=bf16 --ensemble.noise_scale=0.5 --ensemble.samples=4 --policy.num_steps=10` | 2.5초마다 0.2초 멈춘다. 가장 단순하다 (E13) |

피해야 할 조합은 다음과 같다.

- `--ensemble.worker=thread`: 이 로봇에서는 추론이 8배 느려진다.
- 비동기 + `--ensemble.merge=latest` + `commit` 없음: 뚝딱거린다 (E17).
- 동기 + `--ensemble.every`를 50보다 작게: 멈춤이 잦아진다 (E12).
- `--ensemble.coeff`를 `-1.7`보다 작게: 가중치 `exp(-coeff·i)`가 float32에서 inf가 된다.
- `--policy.use_amp=true`: fp16으로 동작하고, 비동기에서는 워커에 적용되지도 않는다.

## `record_ensemble.py`에 추가한 옵션

| 옵션 | 기본값 | 동작 |
|---|---|---|
| `--ensemble.worker=process\|thread` | `process` | 비동기 추론을 별도 프로세스에서 돌린다. 모델을 한 벌 더 올린다(GPU 약 1.2 GB). 관측은 공유 메모리로 넘긴다. 워커가 죽으면 무한 대기하지 않고 1초 안에 에러를 낸다 |
| `--ensemble.noise_scale=S` | `1.0` | 디노이징 초기 노이즈에 곱하는 배수. 0이면 결정적이다 |
| `--ensemble.samples=K` | `1` | 추론 한 번에 노이즈 K개를 배치로 돌려 청크 K개를 평균한다 |
| `--ensemble.merge=average\|latest` | `average` | 도착한 청크를 가중평균으로 합칠지, 통째로 교체할지 |
| `--ensemble.commit=N` | `0`(끔) | 워커는 계속 추론하고, 로봇은 청크 하나를 N스텝 실행한 뒤 갈아탄다. `merge=average`면 그 사이 도착한 청크를 평균해 크로스페이드하고, `latest`면 가장 새 청크로 교체한다. 비동기 전용이고 `every`는 빼야 한다 |
| `--ensemble.profile=true` | 끔 | 종료 줄에 추론 시간 내역을 붙인다. 스레드 워커에서만 의미가 있다 |
| `RECORD_ENSEMBLE_DEBUG=1` (환경변수) | 끔 | 프로세스 워커가 추론마다 구간별 시간을 stderr에 찍는다 |

## 실험 목록

### E1. 비동기 TA 첫 실행 (09-21 19:01, 로봇)

- 구성: `--ensemble.coeff=0.0001`, 비동기(스레드 워커), 나머지 기본값.
- 결과: 추론 29회, 평균 1239.6 ms(최악 2452.5 ms), 도착 지연 평균 23.7스텝(최악 49). 떨림이 심했다.
- 해석: 지연 `k`로 도착한 청크는 앞 `k`개를 잘라내므로 `50 − k`개만 버퍼에 더한다. 그동안 로봇은 `k`개를 소비한다. 버퍼가 마르지 않으려면 `k ≤ 25`여야 한다. 23.7은 그 경계라서 버퍼가 수시로 비었고, `while dry()`가 제어 루프를 추론 한 번(최대 2.45초)만큼 멈췄다.

### E9. fp32 학습 모델을 bf16으로 추론 (오프라인)

같은 입력·같은 노이즈에서 fp32와 bf16의 액션 차이는 RMS 0.003~0.009(최대 0.06)였다. 같은 관측에서 노이즈만 바꿨을 때의 차이(0.14~0.38)보다 30~50배 작다. fp16은 5회 시도에서 NaN이 없었지만 표본이 작아서 계속 피한다. bf16은 `--ensemble.amp=bf16`으로만 걸 수 있다.

### E14. base 드라이버가 GIL을 쥐는지 (오프라인, base 연결, 읽기 전용)

```
기준 (경쟁 없음):             파이썬 루프 20.99 M회/s
update_state() 연속 호출 중:  파이썬 루프  4.53 M회/s (22%)
update_state() 1회 평균 25.1 ms
```

`update_state()`가 도는 동안 다른 스레드의 파이썬은 멈춘다. 제어 루프 48 ms 중 42 ms가 base 호출이므로 워커 스레드가 쓸 수 있는 시간은 6 ms이고, 48 ÷ 6 = 8.0배다. 실측(1173 ÷ 146.7 = 8.0배)과 맞는다.

### E15. 스레드 워커 대 프로세스 워커 (오프라인, 실제 base로 GIL 패턴 재현)

제어 루프가 스텝마다 `update_state()`를 2번 호출하는 조건이다. bf16, 10스텝, K=4, 노이즈 0.5.

|---|---|---|

`--ensemble.coeff`를 빼도 TA는 꺼지지 않는다. 기본값 0.01이 들어간다. 위 런들은 전부 TA가 켜진 상태였다.

### E17. 비동기에서 TA 끄기 (23:12, 로봇) — 나쁨

- 구성: E16 + `--ensemble.merge=latest`.
- 결과: 추론 288.4 ms, 지연 6.1스텝, 20.0 Hz로 E16과 같다. 그런데 정책 구간 클램프가 약 13초에 135회(초과량 평균 0.090 rad, 최대 0.427 rad)였고 로봇이 뚝딱거렸다.
- 결론: 0.3초마다 서로 다른 샘플로 통째로 갈아타면 그때마다 점프가 난다. 비동기 재질의에서는 TA가 그 점프를 흡수한다.

### E18. 미리 받아두기 `every=40` (CPU 시뮬레이션)

추론 0.3초, 제어 20 Hz 가정. `every=50`은 50, 100, 150스텝에서 301 ms씩 막혔다. `every=40 --ensemble.merge=latest`는 막힘 없이 청크당 39~47스텝을 실행했다. 조건은 `every ≤ 50 − (지연 + 3)`이다. 이 방식은 2초에 한 번만 추론해서 GPU가 대부분 쉰다.

### E19~E20. `commit` 모드 (CPU 시뮬레이션)

정답 궤적에 청크마다 σ=3의 오차를 더한 조건. 값은 스텝 간 점프 크기다.

| 구성 | 최대 점프 | RMS | 큰 점프 |
|---|---|---|---|
| commit 없음 + latest (E17 구성) | 9.96 | 1.43 | 51회 |
| commit=40 + latest | 9.71 | 0.81 | 7회 |
| commit=40 + average | 5.71 | 0.58 | 19회 |
| commit=30 + average | 2.35 | 0.34 | 14회 |
| commit 없음 + average (E16 구성) | 1.15 | 0.21 | 1회 |

- 모든 구성에서 막힘 0회, 추론은 쉬지 않고 돌았다.
- `commit=50`을 줘도 새 청크는 갈아타는 시점에 이미 6~10스텝 늦어서 42~43스텝만 실행한다. 쓸 수 있는 최대값은 `50 − 지연`이다.
- 이 표는 부드러움만 잰 것이다. 정확도는 재지 못했다.

### E21. `commit=50`, task02 프롬프트 (09-22 00:21, 로봇)

- 구성: `--ensemble.commit=50 --ensemble.coeff=-1.5 --ensemble.amp=bf16 --ensemble.noise_scale=0.9 --ensemble.samples=7 --policy.num_steps=10`, task = "Pick up the two tubes from the rack with both hands".
- 결과: 추론 90회, 평균 237.2 ms, 지연 4.9스텝(최악 5), 18.6 Hz(약 23초), 클램프 6회.
- 관찰: 맞는 방향으로는 가는데 동작을 끝까지 수행하지 못한다.

### E22. 시연 대비 정확도 (오프라인)

`task02_pickup_tubes`(133 에피소드, 프롬프트 동일)의 실제 프레임 36개(에피소드 6개 × 진행도 6지점)를 정책에 넣고, 예측 청크와 시연자의 실제 다음 50스텝 액션을 비교했다. 체크포인트의 postprocessor를 거친 실제 단위이고 설정당 3회 반복이다.

| 설정 | 팔 RMSE (rad) | 앞 0~9스텝 | 뒤 30~49스텝 | 그리퍼 (m) |
|---|---|---|---|---|
| 기준: 현재 자세 유지(정책 없음) | 0.1642 | 0.0669 | 0.2177 | 0.00785 |
| 10스텝, 노이즈 1.0, K=1 (stock) | 0.1170 | 0.0507 | 0.1510 | 0.00389 |
| 10스텝, 노이즈 0.9, K=7 (E21 구성) | 0.1020 | 0.0452 | 0.1305 | 0.00326 |
| 10스텝, 노이즈 0.5, K=4 | 0.1083 | 0.0453 | 0.1405 | 0.00341 |
| 10스텝, 노이즈 0.5, K=1 | 0.1110 | 0.0464 | 0.1436 | 0.00342 |
| 10스텝, 노이즈 0, K=1 | 0.1096 | 0.0461 | 0.1432 | 0.00334 |
| 25스텝, 노이즈 1.0, K=4 | 0.1019 | 0.0445 | 0.1294 | 0.00336 |
| 50스텝, 노이즈 1.0, K=1 | 0.1194 | 0.0567 | 0.1491 | 0.00414 |
| 50스텝, 노이즈 0.5, K=4 | 0.1074 | 0.0473 | 0.1380 | 0.00331 |

- 샘플링 설정은 정확도를 거의 못 바꾼다. 전부 0.10~0.12 rad 안에 있고, 제일 도움이 되는 건 K(샘플 평균)다. `num_steps=50` 단독은 이 지표에서 오히려 제일 나빴다. 로봇에서 부드럽다고 느낀 것(E10)과 시연 대비 정확도는 다른 축이다.
- 정책은 "가만히 있기" 기준(0.164 rad)보다 35% 정도만 낫다. 학습에 쓴 과제의 프레임치고는 오차가 크다. "방향은 맞는데 끝까지 못 한다"는 증상과 맞는다.
- 열린 루프 오차는 실제 성공률과 같지 않다. 시연 자체가 여러 방식으로 갈리면 오차가 커진다. 해석하려면 아래 비교가 필요하다.
- **후속 비교는 돌리지 못했다**(사용자 중단): (A) 같은 파운데이션 모델을 `task01_move_to_tube_rack`에 평가, (B) 전용 모델 `pickup_tubes_smolvla_kiro_30k`를 task02에 평가. A에서 오차가 훨씬 낮으면 task02가 덜 학습된 것이고, B가 훨씬 낮으면 전용 모델을 쓰는 게 맞다.

## 그 밖에 확인한 사실

- 이 PC의 SmolVLA 체크포인트 8개는 전부 `chunk_size=50`, `n_action_steps=50`이다. 100은 ACT 설정이다(`task03_turn_to_face_beaker_14D`: `chunk_size=100`, `n_action_steps=100`, TE 없음). 가중치에는 청크 길이에 묶인 텐서가 없지만, 학습에서 본 시퀀스가 50스텝이라 추론 때 늘리면 안 된다.
- 체크포인트의 `train_config.json`에는 데이터셋이 `gist/task1-move-to-tube-rack` 하나만 기록돼 있다(step 80000). 이 PC의 어떤 데이터셋에도 "shake"가 들어간 task 문장은 없다. SmolVLA는 프롬프트가 정책 입력이라서, 학습 때 문장과 다르면 동작이 흐려질 수 있다. 실제 학습 데이터와 문장은 학습 서버에서 확인해야 한다.
- lerobot에는 논문 방식의 비동기 추론(`lerobot/async_inference/`, 정책 서버 + 로봇 클라이언트)이 들어 있다. 로봇 타입 검사는 주석 처리돼 있어서 `mobileai_robot`도 받을 가능성이 높다. `grpcio`가 설치돼 있지 않고, `lerobot[async]`로 깔면 protobuf가 6.33.0에서 6.31.x로 내려간다. 시도하지 않았다.
- GPU 전력 제한이 95 W(최대 175 W)다. 병목은 아니었다.
- `_Worker`(스레드)는 워커 스레드가 죽으면 제어 스레드가 `queue.get()`에서 무한 대기한다. 프로세스 워커에서는 고쳤고 스레드 쪽은 그대로다.

## 운영 메모

- 에피소드 저장은 **오른쪽 화살표**다. 왼쪽 화살표는 버리고 다시 녹화, Ctrl+C는 저장하지 않는다. 이번 실험에서는 한 번도 저장되지 않아서 실제 액션 궤적 비교를 하지 못했다.
- 로그는 `2>&1 | tee -i /tmp/이름_$(date +%H%M%S).log`로 받는다. `-i`가 없으면 Ctrl+C 때 마지막 `추론 N회 …` 줄이 잘리고, 파일명이 같으면 이전 로그를 덮어쓴다.
- 읽을 줄: `grep "추론"`(추론 시간, 지연), `grep "Control loop rate" | grep phase=policy`(제어 루프 주파수, 구간별 시간), `grep -c "had to be clamped"`(클램프. 리셋 구간의 것은 리더 암에 맞춰지는 순간이라 정책과 무관하다).
- base over-rotation 배수 = 녹화 런 주파수(21.5 Hz) ÷ eval 런 주파수.
