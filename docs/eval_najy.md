## 매 회차 공통 규칙

- 실행 로그 첫머리에 **`LEROBOT_TASK_ONEHOT=<i>/<K> installed`**, 첫 에피소드에 **`stage i/K active`** 가 보여야 한다.
  **없으면 ESC 로 즉시 중단** — 패치 없이 돈 런은 결과로 쓰지 않는다. (M1·M2·M3 만 해당. B* 는 원핫 없음)
- **exec 는 30** (B* 는 원래 chunk 가 100 — C 단계에서만 100 을 따로 본다).
- **팔 한 틱 이동 상한 0.1 rad** 가 기본으로 걸린다 (`MAX_REL`, 10/06 C-2 부터). 10/06 C-1 이전 회차와 같은 조건이 필요하면 `MAX_REL=none`. 요약의 「잘린 틱」 수를 기록한다.
- **리셋 구간에 터미널의 `POSE taskNN` 줄을 보며 자세를 맞춘다** (1초마다, `pose_guide.py`, 10/06~). `j1 +63→+90↑` = 현재 +63°, 목표 +90°, ↑ 는 각도를 키우라는 뜻(10° 이상 차이만 표시).
  「목표까지」 는 중앙값 자세까지의 거리라 「허용」(최근접 시작점 거리) 보다 크게 나온다 — 0.5 rad 아래면 대체로 허용 근처 [추정]. task08·10 은 중앙값이 참고용. 끄려면 `POSE_GUIDE=0`.
- **이동 단계는 로봇의 시작 위치도 시연 첫 프레임과 맞춘다** — 팔 자세만 맞추고 위치가 다르면 그 회차는 버린다(10/06 task01 두 회차).
  시연 첫 프레임은 `uv run --no-sync python docs/run_logs/2026-10-06_eval_najy/scene_rows.py out.png ~/.cache/huggingface/lerobot/kiroaiseoul/<학습 데이터셋>:0:train` 으로 뽑아 본다.
  task01 = 비커 선반 앞(task11 이 끝난 자리), task03 = 랙 테이블 정면에서 튜브를 든 상태.
- 회차가 끝나면 **rerun 뷰어 창을 닫는다** — 열어 두면 스크립트가 요약 파일을 쓰기 전에 멈춘다(10/06 C-1).
- **시작 자세를 아래 표에 맞춘다** (리셋 구간에 리더암으로). 장면(튜브·비커 위치, 냉장고 문 상태)은 그 단계 학습 시연의
  첫 프레임과 같게 — 단계마다 기준 사진을 한 장 찍어 두고 매번 대조한다.
- 회차가 끝나면 `eval_najy.sh` 가 `scripts/eval_najy_post.sh <회차>` 를 불러 **요약·시작 자세·움직임·지연·베이스 회전/전진**을 재고
  `~/eval_logs/<회차>.report.md` 한 장으로 모은다 (로봇 안 움직임, 파일만 읽음; `docs/run_logs/<날짜>_eval_najy/` 에도 복사). 중단돼서 안 돌았으면 손으로 부른다.
  report 의 `시작점 최근접` 이 표의 「허용」 이하인 에피소드만 그 모델의 판정에 쓴다 (넘으면 ⚠️ 가 붙는다 — 「자세 불일치」 로 따로 적는다).
  이동 단계는 report 의 베이스 회전/전진 **명령·실측**을 「학습 베이스」 줄과 비교한다 (표기 fps 기준과 21 Hz 환산 둘 다 적혀 있다).
- 에피소드가 끝날 때마다 `~/eval_logs/eval_najy_results.csv` 에 한 줄: `run,episode,success(0/1),시작점최근접,비고`.
- 위험하면 비상정지 → 그 회차는 중단 기록. 스크립트 종료 코드가 0 이 아니면 요약 파일과 함께 남긴다.

## 순서

각 단계는 앞 단계가 끝나야 넘어간다. 에피소드 수는 첫 판단용 최소치다.

### A. 이미 있는 기록으로 — 로봇 안 움직임 (10분)

10/02 회차들에서 지연을 잰다:
```shell
uv run --no-sync python scripts/eval_latency_stats.py 1002_1150_m1_t04_e30 --train kiroaiseoul/task04_pour_liquid_from_tubes_to_beaker
uv run --no-sync python scripts/eval_latency_stats.py 1002_1422_base_t05_e30 1002_1438_base_t05_e30 --train kiroaiseoul/task05_tube_disposal
```
남길 것: 베이스 유효 지연(틱·ms)과 t63/t90, 정지 뒤 잔여 회전, **실기 팔 지연(틱) vs 학습 데이터 팔 지연(2틱)**, 추론 스파이크(ms).
베이스 계단이 적어 t63 이 안 나오면 B 의 `measure_base.py latency` 로 잰다.

### B. 정책 없이 재기 — 해석의 기준선 (✅ 10/02 완료 — 위 「지금까지」 표, 다시 할 필요 없다)

| 할 일 | 명령 | 남길 것 |
|---|---|---|
| B-1 녹화 주기 | 각 단계 **녹화 런**의 로그에서 `grep "Control loop rate" <녹화로그> \| grep phase=teleop \| tail -1` | `mean` Hz. 로그가 없으면 같은 조건으로 텔레옵 녹화를 30초 해서 잰다 |
| B-2 베이스 왕복 | `uv run --extra pi0 python scripts/measure_base.py rate` | 출력 전체 |
| B-3 베이스 응답 지연 | `uv run --extra pi0 python scripts/measure_base.py latency` ⚠️ **베이스가 움직인다** — 주변 1 m 비우기 | t63·t90 중앙값 |

> 베이스 속도 명령은 다음 명령까지 유지되므로 **(정책 런 루프 주기) ÷ (녹화 주기) 의 역수만큼 과회전**한다.
> ⚠️ `measure_base` 직후 바로 eval 을 띄우면 베이스 시리얼 포트를 못 잡은 사례가 있다 — 측정 프로세스가 끝났는지 확인하고 띄운다.

### D. 넓고 얕게 — M1 · exec 30 · 단계마다 3ep

A/B 비교를 깊게 하기 전에 11단계 각각에서 **된다 / 정지 / 엉뚱함** 을 먼저 분류한다.

이동 단계에서 볼 것: 회전량(정답 대비), 멈춘 뒤 제자리 유지(떨림/한 방향 표류), `basevel.csv` 의 명령·실측.

#### 텔레옵 구간 — 리더암으로 물체를 쥐고 자세를 잡은 뒤 시작 (10/07 로봇 PC 추가)

`scripts/eval_chain.sh` 는 기본으로 `--teleop.*`(리더암 .3/.2) 를 넘기고, 러너는 **연결 직후·첫 리셋 전에**
lerobot-record 의 「Reset the environment」 와 같은 텔레옵 루프를 한 번 돈다(`runner._run_teleop_phase`).
10/07 bring-up ② 까지는 이 구간이 없어 러너가 연결 즉시 자기 리셋을 시작했고, 사람이 리더암으로 물체를
쥐게 할 틈이 없었다(③·④·⑤ 는 전부 물체를 쥔 채 시작해야 한다).

| 키 | 뜻 |
|---|---|
| `→` | 텔레옵 끝 → 최초 리셋(`reset_pre_NN`)으로. 이게 「시작」 이다. **POSE 줄 앞이 `[→ 가능 ✔]` 일 때만 받는다** — 멀면(`[아직 ✘ R j3 50° > 34°]`) 무시하고 구간을 계속한다(로그 `RIGHT ARROW IGNORED`). 가능해지는 순간 터미널 벨 |
| `←` | 텔레옵 구간을 처음부터 다시(타이머 리셋). 단계 중의 `←` 와 달리 중단이 아니다 |
| ESC | 중단. 첫 단계가 「시작 전 중단」 으로 끝나고 teardown. 연결 중에 눌린 ESC/`←` 도 구간을 돌지 않고 바로 중단이다 |

- 상한 `TELEOP_S`(기본 300 s) — 넘기면 **중단**이다(사람 확인 없이 램프가 시작되지 않는다). `TELEOP=0` 이면 구간 없음(10/07 오전과 같은 동작).
- 구간은 **녹화되지 않는다**(dataset=None). `POSE taskNN` 줄은 첫 단계의 **지정** 시작 자세까지의 거리를 1초마다 찍는다 —
  최초 리셋의 관절별 상한(0.6 rad = 34°)이 `→` 의 조건이다 — 표시만 보면 된다. 팔 한 틱 상한(0.1 rad)·NaN 게이트는 텔레옵 action 에도 걸린다.
- **물체를 든 채 시작할 때는 그 물체를 드는 단계부터** (`FROM_STAGE=3`: 튜브, `FROM_STAGE=6`: 비커) — task01 지정 자세는 빈손 대기 자세라 튜브를 든 팔로는 상한 안에 못 들어간다(10/07 1626 회차가 그렇게 거부됐다).
- **베이스는 구간 동안 0** — 리더 action 의 x.vel/theta.vel 은 「같은 틱에 잰 베이스 속도」 라 토크 켜진 베이스에 되먹임된다(리뷰 10/07;
  eval_najy 리셋 구간도 같은 구조였다). 로봇 위치는 띄우기 전에 손으로 맞춘다. lerobot-record 처럼 손에 따라 움직이게 하려면 `TELEOP_BASE=1`.
  구간이 끝날 때마다 베이스를 한 번 세우고(`teleop_end.stop_base_path`, 실패면 exit 3), 구간 중 예외는 `ended_by: exception` 으로 남는다.
- events.jsonl 에 `teleop_start`/`teleop_end`(`ended_by`: arrow·left_arrow_restart·timeout·esc) 가 남고 보고서에 한 줄로 나온다.
- 단계 **사이**의 텔레옵(예: 정책이 못 집은 튜브를 사람이 쥐여 주고 이어 가기)은 아직 없다 — 그건 `←` 의 의미를 바꾸는 일이라 DGX 와 설계.

#### 띄우기 전에 — 10/06 교차검토로 바뀐 네 가지

1. **`DRY_RUN`·`RESET_ONLY` 는 `=1` 만 쓴다.** `=true|yes|on` 도 받지만 그 밖의 값
   (`DRY_RUN=2`, `DRY_RUN=True1`, 오타)은 **exit 2 로 거부**된다. 옛 판은 `== 1` 비교
   하나였고, 그러면 `DRY_RUN=true` 가 조용히 「꺼짐」으로 읽혀 **명령만 보려던 사람이
   로봇을 움직였다**. 끄려면 변수를 빼거나 `=0`. `FROM_STAGE`/`TO_STAGE` 도 1~11 정수이고
   FROM ≤ TO 여야 하며, 둘 다 `uv run` 보다 먼저 검사된다.
2. **`tmux` 또는 `nohup` 아래에서 띄운다.** SSH 가 끊기면 SIGHUP 이 가고, 러너는 이제
   SIGTERM·SIGHUP 을 받아 teardown(베이스 0 → disconnect)을 탄다 — 옛 판은 Python 기본
   처분대로 **스택을 안 풀고 죽었고 베이스가 마지막 속도를 들고 있었다**. 그래도
   **창을 닫는 것으로 런을 끝내지 마라**: 런을 끝내는 방법은 ESC 다. 두 번째
   SIGTERM 은 **무시**된다(정리 중에 스택을 풀면 팔이 토크 걸린 채 남는다). 정말 급하면
   SIGKILL 이고, 그때는 베이스를 손으로 확인해야 한다. `nohup` 은 그대로 동작한다 —
   `nohup` 이 넘겨 준 SIGHUP 의 `SIG_IGN` 은 **덮지 않는다**(덮으면 nohup 의 목적과
   반대가 된다). 정리가 시작된 뒤에 온 신호도 플래그만 세우고 raise 하지 않는다.
3. **정지 로그를 그대로 믿지 마라.** `stop_base commanded: …` 는 **의도**이고 배달
   확인이 아니다 (`send_action` 은 베이스 쓰기가 실패해도 예외를 내지 않는다 —
   throttled warning 하나다). 이제 홀드 액션 뒤에 확인용 `base.set_cmd_vel(0,0)` 을
   **항상** 한 번 더 보내고 그 bool 을 기록한다. 볼 곳은 events.jsonl 의
   **`stop_base_path`** 다:
   | 값 | 뜻 |
   |---|---|
   | `primary` | 정상. 홀드도 갔고 베이스가 수락했다 (`stop_base_direct_ok: true`) |
   | `primary+direct_failed` | 홀드는 갔고 **확인이 거부됐다 — 베이스가 아직 움직일 수 있다.** exit 3 |
   | `fallback` | 홀드가 실패했고 직접 명령으로 베이스를 세웠다 (팔은 명령 안 함, 안전) |
   | `failed` | 둘 다 실패. exit 3 |
4. **bring-up 은 빈손 → 가벼운 물체 → 유리 기구 순서다.** ②(빈손) 를 통과하기 전에
   물체를 쥐게 하지 말고, ③ 도 **가벼운 플라스틱 튜브 먼저**, 비커·유리 기구는 그다음이다.
   그리퍼를 「매 틱 관측값 재명령」으로 유지하는 것이 쥐는 힘을 보존하는지는 여전히
   **미확인** [추정] 이다.

#### 체인에서만 다른 안전 사항

- **ESC 와 e-stop 을 함께.** 베이스 e-stop 은 팔(별도 이더넷)을 멈추지 않는다 [추정].
  체인은 22단계를 연달아 돌고 사람 입력은 ESC(중단)와 `→`(단계 완료) **둘뿐**이다.
- ESC·`→` 가 무반응인데 에러도 없으면 세션이 Wayland 다 (README 「eval 함정」).
  체인은 preflight 에서 **무조건** 이것을 검사하고 거부한다.
- **`→` 는 리셋 중에 누르지 마라.** 리셋을 끊으면 `not_reached` 가 되고 그건 체인 실패다.
  `→` 는 「정책 단계 완료」 전용이다 (리셋은 스스로 도달을 판정한다).
  눌렀으면 보고서 「사유」 열이 **`사람이 끊음(→)`** 으로 찍힌다 — 상한 초과(램프가 정말
  못 도달)와 구분된다. 종료값은 여전히 `not_reached` 이고 체인은 실패다: 팔이 다음 단계
  시작 자세에 **없기** 때문이고, 아니라고 치고 가면 시연에 없는 자세에서 정책이 출발한다.
- **「출발하지 않음」(`출발 s` 열의 `✗`)은 타임아웃과 다른 발견이다.** 완료 판정에는
  「이 단계가 시작 장면을 떠났다」 는 전제가 있다(팔이 지정 시작 자세에서 0.10 rad 이탈,
  또는 베이스 명령 누적 회전 0.17 rad / 전진 0.10 m). 전제가 안 걸린 채 타임아웃이면
  사유에 `never_departed` 가 붙는다. 그 단계는 **어려워서 실패한 것이 아니라 시작하지
  않았다** — 정책을 보지 말고 시작 장면을 봐라: 바로 앞 리셋의 도달 오차 · 원핫 인덱스 ·
  카메라. (이 전제가 없으면 t03·t04·t10 은 **시작 자세가 자기 끝 자세와 0.001 rad 이내**라
  가만히 서 있기만 해도 「완료」로 떨어진다 — `configs/chain/README.md` 「출발 래치」)
- **「출발」의 기준점은 그 단계의 첫 실측 팔 자세다** — 파일의 지정 시작 자세가 아니다 (10/06).
  `reset.initial: false` + `from_stage > 1` 로 중간부터 이어 돌릴 때 팔을 지정 자세로 끌고 간
  것이 아무것도 없고, 그러면 지정 자세 기준 이탈은 **첫 틱에 이미 참**(가만히 있어도 완료 가능)
  이거나 **영원히 거짓**(지정 자세 쪽으로 움직이는 것이 「집에 가까워지는」 것으로 읽힌다)이 된다.
  첫 실측이 지정 자세에서 0.3 rad 이상 떨어져 있으면 **WARNING 한 줄**이 나오고 판정은 그대로다
  (`stage_end.reason_detail.start_pose_offset_rad`). 그 줄이 보이면 앞 리셋의 도달 오차를 봐라.
- **팔 쪽 출발 래치는 연속 3틱**이 필요하다 (10/06). 래치는 영구적이고 모든 완료의 전제라서
  한 틱짜리 인코더 글리치가 나머지 단계를 통째로 넘겨 버렸다. 베이스 쪽은 **적분**이라 그대로다
  (한 틱으로는 0.17 rad 을 못 넘는다).
- **NaN 은 「안 움직였다」가 아니라 「증거 없음」이다** (10/06). `max(a, nan)` 은 `a` 를,
  `nan >= x` 는 False 를 내므로 신호가 끊긴 것이 **「완벽하게 멈춘 팔이 끝 자세에 정확히 서
  있다」**로 읽혔다 — 완료 조건 그 자체다. 이제 NaN 이 섞인 창은 양방향으로 거부되고,
  **연속 3틱 NaN 이면 감시자가 BLIND** 가 된다(그 단계는 타임아웃 또는 `→` 로만 끝난다).
- **팔 action 에 NaN·inf 가 있으면 그 틱은 hold(관측 팔 값·베이스 0)로 바뀌고 체인이 끊긴다**
  (`exit 4`, 로그에 `NON-FINITE ACTION`). lerobot 의 0.1 rad 클램프는 min/max 쌍이라
  **NaN 을 그대로 통과시킨다** — 이 게이트가 마지막 방어선이다. 원인 후보 둘을 구분하라:
  체크포인트의 손상된 normalizer stats · fp16 오버플로 (README:359).
  ⚠️ **알려진 집계 구멍**: 게이트는 ESC 와 **같은** 플래그(`stop_recording`)로 런을 세우므로
  events.jsonl 에는 그 단계가 `stop_recording`, `trial_end.reason="aborted"` 로 적힌다.
  **종료 코드만** 둘을 구분한다(4 = 모델 실패, 1 = 사람). 따라서
  `eval_chain_report.py`·`aggregate` 의 「사람 중단」 집계에 NaN 실패가 섞여 든다 —
  회차 기록에는 `~/eval_logs/<회차>.log` 의 `NON-FINITE ACTION` 유무를 보고 손으로 적어라
  (`eval_chain.sh` 가 종료 시 그 줄을 찾아 알려 준다).
- **리셋 도달은 창 90% + 「가장 최근 샘플이 tol 안」** 둘 다다 (10/06). 비율만 보면
  「19/21 인데 마지막 둘이 밖」 = 자리 잡았다가 **지금 벗어나는 중**인 팔을 도달로 읽는다.
- 타임아웃·리셋 미도달은 **재시도 없이** 체인 실패다. 다시 하려면 사람이 자세를 보고 새 회차를
  띄운다 — 러너가 자동으로 같은 동작을 반복하는 경로는 없다.
- `exit 3` (베이스 정지 실패) 는 「로봇을 확인하라」 다. 다음 회차를 띄우지 마라.
  **`primary+direct_failed` 도 exit 3 이다** — 위 「정지 로그를 믿지 마라」.

#### 기록

회차마다: 단계별 성공/실패(영상) · 종료 사유(자동/수동/타임아웃) · 리셋 T·도달 오차 ·
단계별 ∫θ·∫x · clamped. 러너가 측정하는 것은 `scripts/eval_chain_report.py` 가 표로 내고
(`~/eval_logs/<회차>.chain.md`), **사람 판정은** `~/eval_logs/eval_chain_results.csv` 에 적는다.

## 결과 넘기기 (DGX 분석용)

로봇 PC 의 두 곳을 DGX `/raid/kiro-ai/eval/real/` 로 옮긴다:
```shell
scp -r ~/eval_logs kiro-ai@<DGX>:/raid/kiro-ai/eval/real/
scp -r ~/.cache/huggingface/lerobot/kiroaiseoul/eval_najy_* kiro-ai@<DGX>:/raid/kiro-ai/eval/real/datasets/
```
DGX 에서는 실패 회차의 실제 카메라 프레임을 모델에 다시 넣어 「모델 예측 자체가 정지인가(장면 차이)」 와
「예측은 움직이는데 실행이 멈추나」 를 가른다. eval 데이터셋은 `push_to_hub=false` 라 허브에는 없다.

## 문제가 생기면

| 증상 | 원인 후보 | 할 일 |
|---|---|---|
| `installed` 줄이 없음 | 패치 미반영 (`uv sync` 안 함, 다른 체크아웃) | 중단 → 「시작 전」 다시 |
| 첫 프레임에 `normalizer`·shape 에러 | 원핫 미적용 / 잘못된 모델 | 로그 첫 50줄 보내기 |
| `robot state is N wide` | `include_velocity` 등 관측 옵션이 켜짐 | 기본 설정으로 |
| 시작 후 팔이 거의 정지, 30틱마다만 움찔 | 시작 자세·장면이 학습과 다름 / 모델 | `시작점 최근접` 확인 → 「허용」 넘으면 자세부터. 맞는데도 정지면 C 의 표 |
| 베이스가 과하게 돈다 | 루프 주기 < 녹화 주기 | 요약의 `mean` Hz 와 B-1 비교 |
| 팔이 청크 경계마다 튄다 | 이음매 | `FIRED` 수 기록 |
| 베이스 통신 전부 실패 | 다른 프로세스(`measure_base` 등)가 포트를 잡음 | 그 프로세스 종료 후 재실행 |
| 끝났는데 요약(`.summary.txt`)이 안 나옴 | rerun 뷰어가 로그 파이프를 잡고 있음 | rerun 창 닫기 (Ctrl-C 하면 요약이 안 남는다) |
| `FileExistsError` | 같은 repo_id 재사용 | 스크립트는 분 단위 이름 — 1분 기다리고 재실행 |
